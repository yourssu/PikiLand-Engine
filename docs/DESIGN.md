# PikiLand Product Design

> 상태: MVP 방향 합의 중 · 마지막 수정: 2026-07-15
>
> 이 문서는 PikiLand의 제품 기준점입니다. 현재 구현은 [README](../README.md), 기술 구조는 [Architecture & Data Pipeline](./ARCHITECTURE_AND_DATA_PIPELINE.md)을 참고합니다.

## 0. Overview

PikiLand는 전담 온콜팀이 없는 소규모 개발팀을 위한 자동 오류 수정 GitHub App입니다. CI·런타임·사용자 행동 오류가 발생하면 관측 데이터와 코드를 함께 분석하고, 실제 재현과 회귀 검증을 통과한 최선의 패치 하나만 PR로 전달합니다. 최종 머지는 사람이 결정합니다.

### 제품 우선순위

1. **정확도:** 원래 오류가 사라지고 다른 기능을 깨뜨리거나 오류를 숨기지 않았다는 근거가 있는 PR을 만든다.
2. **낮은 PR 노이즈:** 재현·검증되지 않은 후보를 사람이 검토할 PR로 공개하지 않는다.

### 한눈에 보는 흐름

```text
오류 감지
  → 코드·로그·행동·릴리스 연결
  → 원인과 패치 후보 생성
  → Harness와 Ralph Loop로 후보별 검증
  → 성공 후보 비교
  → 최선의 PR 하나 + Slack 요약
  → 사람이 머지 결정
```

### 확정된 결정

- 사용자는 Claude 또는 Codex 중 하나를 선택한다.
- Sentry를 필수로 요구하지 않는다.
- 원인과 패치 후보는 여러 개 만들 수 있지만 최선의 하나만 최종 PR로 공개한다.
- 패치 전 오류를 재현하지 못하면 최종 PR을 공개하지 않는다.
- 자동 머지는 하지 않는다.
- MVP는 신뢰할 수 있는 Harness와 Ralph Loop가 준비된 저장소를 대상으로 한다.

## 1. Problem & Scope

### 해결하려는 문제

작은 팀은 오류를 발견해도 로그·사용자 행동·코드를 연결하고, 원인을 추론하고, 패치를 실제 환경에서 검증할 전담 인력이 부족합니다. 개발자는 오류마다 관측 도구, 코딩 에이전트, 테스트 환경과 GitHub를 오가며 같은 작업을 반복합니다.

PikiLand는 다음 승인 지점까지 자동화합니다.

> 문제 감지 → 문맥 수집 → 원인 추론 → 패치 → 실제 재현·회귀 검증 → PR 설명

### 타겟 사용자

- 별도 온콜팀이 없는 소규모 개발팀
- Sentry, PostHog 또는 기존 로그 시스템을 사용하는 팀
- Claude Code 또는 ChatGPT Codex 구독을 이미 보유한 팀
- 자동 머지보다 검증 근거를 보고 사람이 머지하기를 원하는 팀

### MVP 범위

- GitHub App 설치와 저장소 권한 관리
- CI 실패, 런타임 오류, 등록된 행동 규칙 위반 수신
- PostHog·Sentry·서버 로그를 입력 Adapter로 연결
- 코드·로그·행동·프론트·백엔드 릴리스를 Context Bundle로 구성
- 선택한 AI Provider로 원인과 패치 후보 생성
- 기존 Harness와 Ralph Loop를 이용한 Red → Green 및 회귀 검증
- 검증 성공 후보 중 최선의 하나만 PR로 공개
- GitHub에는 개발 근거, Slack에는 쉬운 요약과 링크 제공

### Non-goals

- 자동 머지
- Harness가 없는 저장소의 자동 패치
- 사전 규칙 없이 모든 비정상 행동을 AI가 버그로 판정하는 기능
- Claude와 Codex를 동시에 실행해 경쟁시키는 기능
- 장기 조직 지식 RAG
- Slack 안에서의 승인·머지

후속 아이디어는 [Future Ideas](./FUTURE_IDEAS.md)에 보관합니다.

## 2. Product Flow & Rules

### 사용자 흐름

1. 팀이 GitHub App을 설치하고 AI Provider 하나와 관측 소스를 연결한다.
2. PikiLand가 저장소의 Harness와 Ralph Loop 준비 상태를 확인한다.
3. CI 실패, 런타임 오류 또는 등록된 행동 규칙 위반을 감지한다.
4. 오류 당시 코드·로그·행동·릴리스를 연결한다.
5. 선택한 AI가 원인과 패치 후보를 만든다.
6. 후보별로 패치 전 재현과 패치 후 검증을 실행한다.
7. 성공 후보가 없으면 PR 없이 실패 이유를 알린다.
8. 성공 후보가 여러 개면 근거와 변경 범위를 비교해 최선의 하나만 공개한다.
9. 사람이 GitHub에서 최종 머지 여부를 결정한다.

### Incident 종류

| 종류 | 예시 | 시작 조건 |
| --- | --- | --- |
| Technical Incident | CI 실패, 예외, API 5xx | 명시적인 실패 이벤트 |
| Behavioral Incident | API는 성공했지만 완료 화면으로 이동하지 않음 | 정의된 시작 이벤트 뒤 기대 완료 이벤트가 누락됨 |

MVP에서는 AI가 임의로 이상 행동을 선택하지 않습니다. 팀이 정의한 행동 규칙을 위반한 경우에만 Behavioral Incident를 생성합니다.

### 최종 PR 공개 조건

- 패치 전 환경에서 원래 문제가 재현된다.
- 패치 후 같은 조건에서 문제가 사라진다.
- 오류 부재뿐 아니라 기대한 비즈니스 결과가 발생한다.
- 영향 범위의 기존 정상 흐름이 깨지지 않는다.
- 예외를 무시하거나 실패를 성공처럼 보이게 하지 않는다.
- 같은 Incident가 처리 중이면 새 작업을 만들지 않고 기존 작업에 합친다.

상세 실행 방식은 [Patch & Verification Loop](./ARCHITECTURE_AND_DATA_PIPELINE.md#4-patch--verification-loop)를 따릅니다.

### 결과 전달

| 채널 | 내용 |
| --- | --- |
| GitHub PR | 원인, 근거, 변경 내용, 대안, 재현·검증 결과, 남은 위험 |
| Slack | 쉬운 문제 요약, 사용자 영향, 검증 상태, 프리뷰와 PR 링크 |

MVP에서는 심각도에 따라 Slack 알림을 필터링하지 않습니다. 검증되지 않은 후보를 머지 가능한 PR처럼 안내하지 않습니다.

## 3. Positioning & Roadmap

### 한 문장 포지셔닝

> 팀이 이미 사용하는 관측 도구와 코딩 에이전트를 연결해, 실제 실패의 Red → Green과 회귀 검증을 통과한 최선의 오류 수정 PR 하나를 전달한다.

### Wedge

PikiLand는 PR 생성 자체가 아니라 다음에 집중합니다.

1. 사용자가 이미 보유한 Claude Code 또는 ChatGPT Codex 사용 경로를 활용한다.
2. 한 관측 제품에 종속되지 않고 코드·서버 로그·프론트 행동을 연결한다.
3. 패치 생성에서 멈추지 않고 모델 밖의 Harness로 재현·기대 결과·회귀·오류 은폐를 검증한다.
4. 실패 후보를 버리고 최선의 하나만 공개한다.

경쟁 제품의 최신 비교는 [Competitive Research](./COMPETITORS.md)에서 관리합니다.

### Roadmap

| 단계 | 검증 가능한 결과 |
| --- | --- |
| M0 — Baseline | GitHub 이벤트를 분석해 패치 후보와 Slack 결과를 전달한다. 현재 상태는 README에서만 관리한다. |
| M1 — Foundation | 저장소 준비 상태와 Provider를 설정하고 장시간 작업을 재시도·복구 가능하게 관리한다. |
| M2 — Context | PostHog·Sentry·로그를 코드 및 릴리스와 연결한 Context Bundle을 만든다. |
| M3 — Verified PR | Harness와 Ralph Loop로 후보를 검증하고 최선의 하나만 PR로 공개한다. |

MVP 범위는 M3까지입니다.

## 4. Open Questions & Risks

### 결정 상태와 남은 검증

아래 항목은 모두 같은 의미의 “미결정”이 아닙니다. 제품 원칙은 합의했지만 구현 계약이 필요한 항목과, 공급자·배포 환경을 실제로 검증해야 하는 항목을 구분합니다.

| 항목 | 이미 결정한 것 | 아직 확정할 수 없는 이유 |
| --- | --- | --- |
| Harness 계약 | 재현·기대 결과·회귀·오류 은폐를 구조화해 판정한다. | 언어와 테스트 도구가 다른 저장소에서도 쓸 명령·입출력 스키마를 실제 예제로 검증하지 않았다. |
| Ralph 종료 | Harness가 성공을 판정하고 무한 반복은 허용하지 않는다. | 후보당 반복 수, 무진전 기준, 시간·사용량 예산을 아직 합의하지 않았다. |
| Claude·Codex 실행 | Provider별 인증과 실행을 분리한다. | 개인 구독의 무인 실행 지원 범위가 공급자마다 다르므로 공식 경로와 PoC 확인이 필요하다. |
| 프론트 artifact | 오류 당시 버전을 필수 검증하고 최신 버전이 다르면 추가 검증한다. | 실제 배포 시스템이 artifact를 얼마나 보관하며 어떤 방식으로 복원할 수 있는지 정해지지 않았다. |
| 성공 후보 비교 | 증거 강도, 회귀 결과, 변경 크기, 복잡도, 되돌리기 용이성으로 비교한다. | 원칙은 결정됐다. 동점 처리나 수치 가중치만 구현 단계에서 확정한다. |
| 초기 배포 | Probot Control Plane, PostgreSQL Queue, 격리 Worker로 역할을 분리한다. | 논리 구조는 결정됐다. 예상 부하·보안·비용을 확인한 뒤 실제 호스팅 제품과 프로세스 수를 선택한다. |

### 주요 리스크

| 리스크 | 원칙 |
| --- | --- |
| 작은 팀에 Harness가 없을 수 있음 | MVP 지원 대상을 좁히고 자동 Harness 생성은 후속으로 둔다. |
| 관측 데이터 연결이 불확실함 | 추측하지 않고 재현 불가로 종료한다. |
| AI가 오류를 숨기는 패치를 만듦 | 모델 밖 Harness가 기대 결과와 회귀를 판정한다. |
| 구독 기반 자동화가 공급자 정책과 맞지 않음 | Provider별 PoC 후 지원 범위를 확정하며 API처럼 임의 사용하지 않는다. |
| 로그·개인정보가 PR에 노출됨 | 원문은 임시·비공개로 처리하고 PR에는 정제된 근거만 남긴다. |

관측 데이터 연결이 불확실하면 그 사실을 숨기지 않습니다. 결과에는 연결 상태, 부족한 식별자, 후보로 사용한 데이터와 재현 여부를 표시합니다. 불확실한 연결에서 시작했더라도 Harness가 독립적으로 원래 오류를 재현하면 작업을 계속할 수 있지만, 재현하지 못하면 최종 PR을 공개하지 않습니다.
